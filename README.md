# APP Opportunity Research

本项目的目标是系统性发现“客户需求量大、现有产品体验不足、具备变现空间”的 APP 机会，并把候选方向推进到可验证、可开发、可盈利的产品方案。

## 核心假设

高下载量说明市场已经存在客观需求；低评分说明用户满意度不足。二者同时出现时，往往代表一个值得研究的机会：用户需要这类产品，但现有解决方案没有做好。

这个假设需要进一步过滤。不是所有低评分热门 APP 都适合复制或优化，有些领域存在强监管、强版权、强平台资源、强网络效应，或者依赖线下履约能力。项目研究必须把“需求大”与“我们能做得更好并赚钱”同时纳入判断。

## 机会筛选模型

候选 APP 的机会分建议按以下维度评估：

```text
机会分 = 需求强度 * 痛点强度 * 变现潜力 * 可实现性 / 竞争壁垒
```

### 1. 需求强度

优先观察：

- App Store 和 Google Play 排行榜位置
- 下载量或安装量区间
- 评论数量和近期评论增长
- 搜索热度、关键词热度、同类竞品数量
- 使用频率：日常刚需优先于低频娱乐或一次性工具

### 2. 痛点强度

低评分本身不是结论，需要分析差评内容是否集中。优先关注反复出现的问题：

- 广告过多或干扰核心流程
- UI 复杂、操作效率低
- 功能缺失或关键功能不稳定
- 收费不透明、订阅陷阱、退款困难
- 性能差、崩溃、加载慢
- 本地化差、客服差、隐私担忧

如果差评分散且不可被产品设计解决，机会价值下降。

### 3. 变现潜力

优先选择已经被市场验证过付费意愿的方向：

- 订阅制 SaaS 或个人效率工具
- 高频使用的生活服务、工作流工具、教育工具
- 可通过高级功能、模板、自动化、AI 能力收费的产品
- 可通过 B2B、团队版、专业版扩展收入的产品

单纯依赖广告的 APP 需要谨慎，除非用户规模和分发能力非常明确。

### 4. 可实现性

优先选择可以用小团队 MVP 验证的方向：

- 不依赖复杂线下履约
- 不需要大量版权内容
- 不需要强平台牌照或监管审批
- 不强依赖社交网络效应
- 可以通过 API、AI、自动化、优秀 UX 或本地化形成差异

### 5. 竞争壁垒

需要避开的高风险方向：

- 平台型社交、即时通讯、大型电商
- 金融、医疗、法律等强监管产品
- 高版权内容分发
- 需要大规模商家、司机、老师、医生等供给侧网络的业务
- 已被巨头产品免费覆盖且没有清晰细分场景的工具

## 调研流程

1. 收集热门 APP
   - 来源包括 App Store、Google Play、Sensor Tower、data.ai、Similarweb、公开榜单、行业报告和关键词搜索结果。
   - 按分类记录：效率、教育、健康、财务、生活、本地服务、创作工具、AI 工具等。

2. 建立候选表
   - 记录 APP 名称、平台、分类、评分、评论数、安装量、榜单位置、主要变现方式、竞品链接。

3. 分析差评
   - 抽样最近 100-300 条低评分评论。
   - 将问题归类为广告、价格、功能、稳定性、性能、设计、隐私、客服、本地化等。
   - 统计高频痛点，而不是只摘录个别情绪化评论。

4. 评估商业机会
   - 判断是否有明确付费用户。
   - 判断是否能用 MVP 做出明显更好的核心体验。
   - 判断是否能通过 AI、自动化、模板、垂直人群、本地化或更透明定价切入。

5. 输出候选方向
   - 每个方向必须包含目标用户、核心痛点、竞品缺陷、MVP 功能、差异化方案、变现方式和主要风险。

## 推荐使用的官方技能和插件

官方来源以 OpenAI Skills Catalog 和 Codex 内置/curated skills 为准：

- OpenAI Skills Catalog: https://github.com/openai/skills
- Skill Installer: https://github.com/openai/skills/blob/main/skills/.system/skill-installer/SKILL.md

建议优先使用或安装：

- `openai-docs`：查询 OpenAI API、模型选择、AI 功能集成和官方文档。
- `chatgpt-apps`：设计 ChatGPT Apps、MCP Apps bridge 或 AI 应用原型。
- `playwright` / `playwright-interactive`：做 Web APP 自动化测试、截图验证和端到端流程检查。
- `figma` / `figma-generate-design` / `figma-implement-design`：做界面设计、设计系统和从设计到实现的交付。
- `security-best-practices` / `security-threat-model`：在涉及账号、支付、隐私、用户数据时做安全设计。
- `vercel-deploy` / `netlify-deploy` / `cloudflare-deploy`：部署 Web APP 或 MVP。
- `winui-app`：如果方向是 Windows 桌面 APP，可用于本地客户端开发。

可用 Codex 的 `$skill-installer` 安装 curated skills。安装后需要重启 Codex 才能加载新技能。

## 项目阶段

### Phase 1: 市场机会研究

目标是找出 20-50 个候选 APP，并按机会分排序。

交付物：

- 候选 APP 表
- 差评痛点分类
- 初步机会分
- 5-10 个优先研究方向

### Phase 2: 产品方向选择

目标是从候选方向里选择 1-3 个最适合 MVP 的 APP。

交付物：

- 产品机会说明
- MVP 范围
- 核心用户路径
- 商业模式假设
- 风险清单

### Phase 3: MVP 设计

目标是把选定方向转成可开发规格。

交付物：

- 产品需求文档
- 页面和功能清单
- 技术栈建议
- 数据和 API 需求
- 验证指标

### Phase 4: 开发和验证

目标是做出可运行 MVP，并验证用户是否愿意使用或付费。

交付物：

- 可运行 APP
- 自动化测试
- 部署链接
- 用户反馈记录
- 下一轮迭代计划

## 当前下一步

第一步不是直接开发 APP，而是建立数据驱动的机会池。建议先完成 20-50 个候选 APP 的收集和评分，再选择一个 MVP 方向进入产品设计。
